## 一、分层

```
qbank.core      领域模型 / 存储 / 内容渲染 / 查重。零 UI、零 Web 依赖
qbank.exchange  导入器 / 导出器 / pandoc 封装
qbank.web       FastAPI + Jinja2 页面
qbank.cli       Typer 命令行
```

`core` 与 `exchange` 不得 import `web`——这条由 `tests/unit/test_layering.py` 用
AST 强制检查，不是靠自觉。它是「后续可以部署成 Web 端」这个目标唯一的技术保障：
只要界面层没有渗进内核，换前端或换部署形态就不需要动业务代码。

`app.py` 是组装根，它 import 全部 router；所以 `render` 放在 `templating.py` 而不是
`app.py`——否则 router 要反向 import 组装根，形成 import 环（运行时靠延迟导入能
绕过去，但 mypy 会因此看不到 router 模块的属性）。

## 二、中文检索：字符 n-gram，不是分词

**结论**：连续中日韩字符切成**一元 + 二元**，拉丁字母与数字整段保留，写进
FTS5 的 `unicode61` 列。

### 为什么不用 SQLite 自带的分词器

实测（SQLite 3.37）：

| 查询 | `trigram` | `unicode61` |
|---|---|---|
| `函数` | 0 条 ❌ | 整句一个 token，查不到 |
| `性质` | 0 条 ❌ | 同上 |
| `二次函` | 1 条 | — |

`trigram` 要求查询串 ≥ 3 字符，而中文检索词绝大多数是 2 字。

### 为什么不用 jieba 分词

最早就是 jieba 方案，踩了一个很隐蔽的坑：**jieba 的切分结果依赖上下文**。

| 输入 | `cut_for_search` 结果 |
|---|---|
| `用 Dijkstra 求最短路径` | `用 dijkstra 求 最 短 路径` |
| `最短路径`（单独作为查询串） | `最短 路径` |

索引里只有 `最`、`短`，查询却要求 `最短` —— 这道题**在库里但搜不到**。

「索引端和查询端调同一个函数」挡不住这个问题，因为函数本身不是上下文无关的。
字符 n-gram 没有这个问题：同样的字符串在任何位置都切出同样的 token。

### 两个必须记住的细节

- **一元是必须的**。`栈`、`图`、`树`、`环` 这些单字术语在理工科题库里极常见，
  只索引二元组的话这些查询全部失效。
- `unicode61` 把 `+ # .` 当分隔符，于是 `C++` 和 `C#` 都退化成 `c`。归一化阶段
  换成别名（`cpp` / `csharp` / `dotnet`），索引端与查询端共用同一张表。

代价是子串式命中：搜 `短路` 会命中「最**短路**径」。题库场景里召回比精确重要
——多出几条让人扫一眼，远好过「明明有这道题却搜不到、只好重新录一遍」。

相关代码：`qbank/core/content/segment.py`，回归测试在 `tests/unit/test_segment.py`。

## 三、查重：精确指纹自动化，近似只排序给人

### 实测结论：不存在可用的相似度阈值

最初的设计是 simhash + 汉明距离阈值。字符 2/3/4 元组与词级都试过，**任何单一
阈值都分不开「同一道题的变体」和「语义相反的不同题」**：

| 3 元组 Jaccard | 一对题目 | 实际应判为 |
|---|---|---|
| 0.625 | 「…复杂度**是**多少」/「…**为**多少」 | 同一道题 |
| 0.600 | 「…说法**正确**的是」/「…说法**错误**的是」 | **不同的题** |
| 0.600 | 「求 f(x) 的**导数**」/「求 f(x) 的**积分**」 | **不同的题** |
| 0.600 | 「…+2x+**1**…」/「…+2x+**3**…」 | 同一道题 |
| 0.455 | 「二次函数的图**像**」/「图**象**」 | 同一道题 |

同题变体最低 0.455、异题最高 0.600，区间交叠。根因很简单：**改一个字就能把
题意反过来**，而任何表面相似度都看不出这层语义。

所以职责划分是：

- **精确指纹**（SHA-256）：可靠，可以驱动自动动作（自动跳过、自动更新）
- **相似候选**：只排序给人确认，阈值偏向召回（误报只是多看一眼，漏报是库里多
  一道重复题）

这个结论被固化成了测试 `test_no_threshold_separates_variants_from_distinct_questions`：
哪天它失败了（说明找到了可分的度量），才可以重新考虑自动判重。

### 答案进指纹，但不进相似度

这个差别是刻意的，而且很要紧。实测：

```
「栈是一种先进先出的线性表／答案：错误」
「栈是一种后进先出的线性表／答案：正确」
```

题意被一字反转，答案也跟着反转。只比题干相似度 0.538；把答案算进去掉到
**0.412**，低于 0.45 的阈值——这道**最需要人工复核**的题反而被静默漏掉。

根因：题意一旦反转，答案必然跟着反转，于是答案贡献的是额外的**差异**，恰好
压低了我们最想抓到的那一类。

答案仍然要进指纹——同题干不同答案是两道题，不能自动跳过。

### 既然要人判断，就必须让人看见差异

导入预览页把差异逐字高亮：

```
下列哪些属于{+非+}线性结构？          一个字，题意完全相反
栈是一种[-先-]{+后+}进先出的线性表。   一字之差，答案也跟着反转
```

按**字符**而非按词比对（中文没有词边界，要抓的恰恰是一两个字的改动），比对前
先转纯文本（`**粗体**` 和 `__粗体__` 不该显示成差异）。差异只有几个字时额外
标注——这种情况最危险，相似度反而很高，最容易被当成重复直接跳过。

删除线/下划线与颜色同时使用，色觉障碍用户也能分辨。

### 判定规则必须和写入规则一致

`check_duplicates`（预览用）和 `upsert`（写入用）走**完全相同**的判定顺序：
`external_id` 优先，其次指纹。

曾经不一致过：先用 docx 建库、再用同内容的 md 重新导入，pandoc 往返让题面产生
细微差异 → 指纹对不上 → 预览说「将要新建」，而 upsert 凭编号认了出来、实际跳过。
**预览存在的全部意义就是让用户事先知道会发生什么**，说一套做一套比没有预览更糟。

### 规模

查重曾经是灾难性的：往 2000 道题的库里导 300 道，光预览要 **843 秒**。根因是
每道待导入的题都为全部候选重算一遍 shingle，而算 shingle 要解析一遍 Markdown。

拆开测：

| 环节 | 耗时（2000 条候选） |
|---|---|
| SQL 取候选 | 271 ms |
| 取 parts（ORM 惰性加载） | 1287 ms |
| 算 shingles（解析 Markdown） | 1238 ms |
| 2000 次 Jaccard 比较 | **14 ms** |

比较本身只占 14 毫秒，其余全是重复的加载与解析。三处改动：

1. 候选集整份文件只建一次（`DuplicateIndex`）
2. 候选查询补 `selectinload`（惰性加载 answer/sub_questions 会退化成几千条 SQL）
3. 长度界剪枝：`Jaccard ≤ min(|A|,|B|) / max(|A|,|B|)`。这是可证明的上界，
   按它跳过不可能达标的候选绝不会漏掉真匹配，代价只是两次整数比较

**843s → 15s**。剪枝的无损性用 300 轮随机数据对照朴素实现验证
（`test_length_bound_pruning_never_changes_results`）。

相关代码：`qbank/core/services/dedup.py`、`qbank/core/content/diff.py`。

## 四、内容格式：Markdown + LaTeX

题目内容统一存成 Markdown + LaTeX + GFM 表格，图片引用写成
`asset://<sha256>` 而不是文件路径。

这一个决定同时解决四件事：各种导出格式都从它派生、整库搬迁不断链、图片按内容
去重、文本可做查重指纹。

### 字面 `$` 是这一层最大的坑

题干里出现字面的 `$` 很常见：金额 `$5`、shell 变量 `$HOME`、C 的格式串。
三道措施挡住误判：

1. 所有改写先经 `split_protected` 隔离围栏代码块、行内代码与 HTML 注释
2. 解析器关掉 `allow_space`。开着的话「价格 $5 和 $10，变量 $HOME」里的
   `$5 和 $` 会被当成行内公式，正文被悄悄改坏
3. 带空格的 `$ x^2 $` 由归一化预先收紧，**且仅在**内容含 `\`、`^`、`_` 等强
   数学信号且不含中文时才动手

所以模板规范里写明：**行内公式两侧不要留空格**。

### 公式交给前端时用 `\(...\)` 而不是 `$...$`

这样 KaTeX 之类的前端不必去扫 `$`，字面 `$` 才安全。

### 界面用 MathML，不用 KaTeX

服务端把 LaTeX 转成 MathML，浏览器原生渲染。不需要 KaTeX 的 JS 与约 1.2 MB
字体文件，界面因此完全离线可用。代价是复杂公式的排版不如 KaTeX。

导出也沿用了这一条：html 与 pdf 走 MathML（单文件、断网能看、Chromium 打印时
不必等任何外部资源），docx 走 pandoc 转成 Word 原生的 OMML——那一路比 KaTeX
还好，公式在 Word 里可以直接编辑。所以始终没有引入 KaTeX。

## 五、导入：三种格式共用一个解析器

docx 和 html 都先由 pandoc 转成 Markdown，再走与 md 完全相同的块解析器。
维护成本降为三分之一，而且 pandoc 顺带解决了两个最麻烦的问题：Word 的 OMML
公式自动转 LaTeX、内嵌图片自动落盘。

### pandoc 参数每个都有踩过的坑

| 参数 | 原因 |
|---|---|
| `-tex_math_gfm+tex_math_dollars` | gfm 默认把公式输出成 GitHub 的 ``$`x^2`$`` 而非 `$x^2$` |
| **保留** `raw_html` | 关掉它图片会变成 Markdown 语法（省事），但**合并单元格的表格会被悄悄拍平**，试卷里这种表很常见 |
| `--wrap=none` | 默认在 72 列折行，会把 `【题干】` 这类标记行拦腰截断 |
| 不加 `tex_math_single_backslash` | gfm 不支持，pandoc 会直接报错退出 |

保留 `raw_html` 的代价是带尺寸的图片以 `<img>` 形式出现（不是 Markdown 语法），
所以图片吸收与渲染两处都要同时处理两种写法。

### 示例文件由一份源头生成

`docs/examples/` 下的 md / docx / html 三份示例，由
`scripts/生成模板示例.py` 从同一份 Markdown 生成，生成时顺带做往返检查。

这个自测第一次跑就抓出五个真 bug：选项挤在一行只认出 1 个、pandoc 把 `*` 转义成
`\*` 导致正确项标记全部失效、行末 `【答案】` 后接下一段时值丢失、行中 `【解析】`
被吞进答案、`/` 分隔备选答案时把 `</span>` 也切开。

### 先预览、后确认，绝不静默导入

来源是几十份历年 Word 文件、一次几百道题。静默导入一旦出错（格式误判、重复
覆盖），用户发现时已经不知道改了什么——而题库是他们唯一的一份资料。

暂存的是**上传的文件**而不是内存里的计划：解析一份几百道题的文件只要几十毫秒，
重复做的代价微不足道，换来预览页可刷新、可改策略重看、服务重启不丢、没有任何
需要过期清理的内存状态。

## 六、存储

### SQLite 的两个默认值会坑人

- `PRAGMA foreign_keys` 默认 **OFF**。不显式打开，模型上写的
  `ondelete="CASCADE"` 全部不生效，删课程会留下一堆悬挂题目
- 默认 `journal_mode=DELETE` 下读写互斥，改成 WAL 后「一边浏览列表、一边后台
  导入」才不会互相阻塞

### 时间列必须用 `UtcDateTime`

SQLite 上 `DateTime(timezone=True)` 写进去是带时区的，**读回来却是 naive 的**。
拿它和 `datetime.now(timezone.utc)` 相减会直接抛 `TypeError`——而「避开近 180 天
用过的题」正好要做这个减法。

### 枚举列必须用 TypeDecorator

把列声明成 `String(20)` 而注解写成 `Mapped[TagCategory]` 时，SQLAlchemy **不会**
在读出时把字符串转回枚举，拿到的是裸 `str`，于是 `tag.category.label` 直接
`AttributeError`。靠调用方到处写 `TagCategory(...)` 能绕过去，但那是个陷阱：
漏一处就炸一处，而且只在运行时才发现。

### 几个结构性决定

- **主键用 UUID**：为「导出整库给同事导入」做准备，自增 id 跨库必然冲突
- **章节用物化路径**：让「某章及其子章节下的题」变成一次 `LIKE`，不必递归查询。
  代价是移动或重命名必须重写整棵子树，这件事只在 `ChapterRepo` 里做
- **试卷存题面快照**：去年的卷子不该因为今年改了题而变样
- **软删除**：所有读方法默认过滤 `deleted_at IS NULL`。忘记过滤的后果是已删除的
  题悄悄出现在组卷结果里，而反过来最多是回收站看起来是空的

### 图片按内容哈希存储，且不自动压缩

同一张图被多道题引用只存一份；正文里写 `asset://<sha256>` 而非路径，搬目录不断链。

**不自动压缩**：压缩会改变字节内容也就改变哈希，去重直接失效；而且有损重编码
可能糊掉用户的电路图或几何图。现在是原样存储 + 在导入报告里提示尺寸偏大，
由用户自己决定。

## 七、界面

零前端依赖：服务端渲染的 Jinja2 + 约 400 行原生 JS。

没有引入 HTMX——界面真正需要 JS 的只有四件事（实时预览、图片粘贴、动态增删行、
深浅色），原生写完一共一百多行，不值得引入一个库。将来需要替换也是直接替换。

### 三个不可撤销的操作都要求手打确认词

删课程要手打课程名、清空回收站要输入「清空」、清理孤儿图片要输入「清理」。
一个「确定吗」对话框挡不住误点，而题库是用户唯一的一份资料。

### 校验失败必须回填

老师写一道综合题可能花十分钟，不能因为漏填一个分值就把整页清空。

### 一个浏览器 DOM 的坑

单选↔多选切换时，正确项的输入要在 radio 和 checkbox 之间转换。转换中途会短暂
出现「同一个 radio 组里多个选中」的非法状态，此时把其中一个设为 `false`，
浏览器会把**整组**都取消掉。必须分三步：先全部清空 → 统一改类型 → 最后回填。

## 八、组卷：精确匹配，不是贪心

### 为什么不是「分层抽样 + 贪心」

一道题只能用一次，而各节的候选池是**重叠的**（第一节要「难度 3 的单选」、第三节
要「第 2 章的单选」，同一道题两边都够格）。于是这不是几次独立抽样，而是一个
「谁占用谁」的分配问题。

贪心能解开绝大多数情况，但解不开的时候它分不清两件事：

- 库里确实没这么多题（该改蓝图）
- 库里够，只是先抽的那几道正好把后面需要的题占掉了（该换抽法）

把后者报成「题库不够」，和静默降级一样糟——老师会以为自己得去出新题，而实际上
只要换个抽法就有。

所以 `qbank.core.services.selection.solve` 把它当**二分图匹配**精确求解（增广路，
Kuhn 算法）：把「第 N 节难度 D 要 3 道」摊成 3 个空位，空位与够格的题连边，求最大
匹配。匹配满了就是真能组出来，匹配不满就是**真的**凑不齐，不存在「算法没找到」
这种中间状态。

最小的反例（`tests/unit/test_selection.py::test_backtracks_instead_of_reporting_a_false_shortage`）：
第一节有 `{q1, q2}` 可选要 1 道，第二节只认 `{q1}` 要 1 道。贪心按顺序先给第一节
`q1`，第二节就没了；匹配会让第一节改拿 `q2`。

### 缺额诊断是推导出来的，不是猜的

某个空位增广失败时，那次深搜访问过的题目集合恰好就是它能触及的全部可用题
（`N(S)`），访问过的抽题单元集合就是 `S`。按 Hall 定理 `|N(S)| < S 需要的空位数`
必然成立——这一步在代码里是一句 `assert`，推导错了宁可当场炸掉，也不要报一个
「需要 3 道、有 5 道、缺 -2 道」的荒谬结论。

于是报告能直接说出是哪几节在抢同一批题，而不是含糊地说一句「组卷失败」。

**每个没凑齐的单元都必须有一条自己的说明**。早先的写法是按 Hall 违反集合报告、
并丢掉「被别的集合包含」的那些，结果出现过这种报告：概览写着「第二节 3/4 道」，
底下的原因里却只提第一节。缺了一道却没人解释为什么，比报得啰嗦糟糕得多。

此外，缺额还会附上**放宽哪一条能多出几道**：逐条把筛选条件摘掉再数一遍，差额
大的那条就是真凶。「符合条件的只有 1 道」这句话本身没法行动。

> 刻意**不**探测题型这一条：对一个标题就叫「综合应用题」的大题说「放宽题型可多出
> 15 道」毫无可操作性，只会把真正有用的几条提示挤下去。

### 可复现的确切含义

**同一题库状态 + 同一份蓝图 + 同一个 seed = 同一份卷**。这要求候选池的初始顺序
本身是确定的：SQL 不保证没有 `ORDER BY` 时的行序，所以 `QuestionRepo.ids` 一律按
id 排序后再用种子打乱。少了那句 `ORDER BY`，同一份蓝图在两次运行、两个平台上
可能抽出不同的题，而这种不一致极难察觉——每一份卷子单看都是合理的。

选项乱序**另起一条随机流**，按「种子 + 题目 id」单独播种，不复用抽题那条。抽题
消耗多少随机数取决于候选池大小，一旦复用，往题库里加一道无关的题就会让整卷的
选项顺序全变。

「题库状态」包括使用记录，而成卷本身会写使用记录。所以设了
`avoid_used_within_days` 时，原样重跑一次蓝图得到的是**不重题的另一套**，不是
同一套。这是出 B 卷想要的行为，但很容易被误当成「可复现坏了」，所以
`tests/unit/test_paper.py` 里专门钉了一条用例。

复现一份旧卷靠的是**卷子本身**，不是重跑蓝图——见下。

### 题面快照：去年的卷子永远是去年那张

`PaperItem.snapshot` 存的是成卷那一刻完整的 `QuestionDraft`，而不是「题目 id +
版本号」。卷子要能在原题被改、被删、甚至整个课程被删之后照样原样印出来。多占的
那点空间换来的是教学场景的一条硬要求：学生来查分时看到的得是当时那张卷。

`question_id` 保留着，用于「跳到原题」与使用统计，原题被彻底删除时它变成 `NULL`，
卷面不受影响（界面会标一句「原题已删除」）。

### 使用记录是镜像，不是流水

`question_usage` 不手工增删，而是每次改动后按当前题目项**重算**
（`PaperRepo.sync_usage`）。加题、删题、挪题、整节删除都会影响它，每处各写一遍
增删迟早会漏。

`exclude_used_within_days` 的查询会跳过回收站里的卷子：试着组几次卷再删掉，不该
把那批题封印几个月，而用户完全看不出是什么原因。

### 选项乱序后答案必须跟着换

选项一打乱，原来写着「B」的答案就错了。重排后选项会**重新编号**成 A/B/C/D——
卷子上「C.」排在第一个位置，学生只会以为印错了。

答案只在**整体只是标号**时重算（`B`、`ACD`、`A、C 和 D`）；写了别的内容
（「B，因为栈是后进先出」）时保持原样——擅自改写一段话比留着一个需要人工核对的
答案更危险。

## 九、导出：两条管道，不是四条

四种格式看着是四件事，其实只有两条管道：

```
Paper → 上下文 ─┬→ md 模板  → Markdown ─┬→ .md（图片旁挂）
                │                       └→ pandoc → .docx
                └→ html 模板 → HTML ────┬→ .html（图片内联，单文件）
                                        └→ Chromium → .pdf
```

docx 是 Markdown 转出来的，pdf 是 HTML 打印出来的。于是「题号怎么排、分值印在
哪、答案放哪一段」只定义两次而不是四次——四套模板各写一遍的下场是迟早出现
「Word 版和 PDF 版题号不一样」，而且谁也说不清哪边才对。

### 上下文里存 Markdown 原文，不存渲染结果

模板拿到的 `item.stem` 是 Markdown。md 模板直接用，html 模板过一个 `md` 过滤器。
反过来（上下文里直接存 HTML）的话，md 导出就得把 HTML 再转回 Markdown——一次
无谓的往返，而且必然有损。

### 同一份卷导出两次字节一致

产物里**不写导出时间**。要时间戳的话试卷自己的创建时间更有意义，而「两次导出
完全一样」换来的是：改了模板重新导出可以直接 diff 看改了什么，导出本身也能进
测试（`tests/integration/test_export.py` 里就有一条）。docx 除外——pandoc 会往
文件里写时间戳，这个控制不了。

### 图片：三种目标，三种解析方式

| 目标 | 形式 | 为什么 |
|---|---|---|
| html / pdf | `data:` 内联 | 单文件发给学生，断网能看；打印时不等网络 |
| docx | **绝对路径** | pandoc 找不到图时**不报错**，只静默输出一个没有图的文档 |
| md | 旁挂目录 + 相对路径 | .md 要能提交进 git、再加工，base64 会让它读不了也 diff 不了 |

图找不到时一律换成「［图片缺失］」并计数。留一个坏引用的话，用户看到的是
Word 里的红叉或网页上的破图图标——他以为「这张图坏了」，而实际是「这张图没
带过来」，排查方向完全不同。

### PDF：先找系统浏览器，别急着下 130MB

原计划是 Playwright 自带的 Chromium。实测在本机（macOS 12）上
`playwright install chromium` 直接报 `does not support chromium on mac12`，
一个字节也下不下来——而同一台机器上装着 Google Chrome。

所以改成按「自带内核 → 系统 Chrome → 系统 Edge」依次尝试，**真的启动一次**再
判定可用（文件在不等于能跑起来：内核目录残缺、系统版本不支持、缺共享库，都是
文件在而起不来）。多数人机器上本来就有 Chrome，于是既省掉那 130MB，也让下不动
内核的平台能正常出 PDF。

为什么不用 WeasyPrint 一类的纯 Python 方案：它不支持 MathML，公式会整片变成
乱码。试卷里有公式、合并单元格的表格、代码块，这些东西的排版规则浏览器实现得
最全，而 PDF 要的正是「和浏览器里看到的一样」。

### 选项乱序后答案必须跟着换

这是导出里最危险的一处。选项一打乱，原来写着「B」的答案就错了。重排后选项会
**重新编号**成 A/B/C/D——卷子上「C.」排在第一个位置，学生只会以为印错了。

答案只在**整体只是标号**时重算（`B`、`ACD`、`A、C 和 D`）；写了别的内容
（「B，因为栈是后进先出」）时保持原样——擅自改写一段话比留着一个需要人工核对的
答案更危险。

### 学生卷里不能有答案

听起来是废话，但它是一条**有测试守着**的硬约束
（`test_student_copy_contains_no_answers`）：答案、解析、评分标准三者在
`paper` 版面里都不能出现。模板改错一个 `{% if %}` 就会泄题，而泄题这件事印完
才发现就晚了。

### 模板写错要当场报错

Jinja 用 `StrictUndefined`。引用一个不存在的字段会抛异常，而不是渲染成空白——
默默空白的后果是老师印完一百份才发现分数没了。

## 十、交换包与打包

### `.qbz` 是唯一的恢复手段，所以它要装得回去

删课程是硬删除——连题目与试卷一起没，没有回收站也没有撤销。所以这个包的判据
不是「能导出一份题目」，而是**删掉整门课之后能原样装回来**：题目、章节、标签
分类、图片、试卷、检索索引，一样都不能少。这条写成了测试
（`test_restores_a_deleted_course`）。

包里**不含**修改历史与导入批次记录。它们是本地的操作痕迹，对「把题库搬到另一台
机器」没有意义，而带上会让包大出几倍。这一条写在 manifest 的 `excludes` 字段里，
免得将来有人以为是 bug。

### 题目的 UUID 跨库保持不变

导入时沿用包里原来的 id，而不是新生成一个。不沿用的话，「发给同事 → 他改几道 →
再发回来」就不成立：题面改过之后指纹对不上，而 id 又变了，于是收回来的包被当成
一批新题再建一遍，库里每道题都有两份。UUID 天然不冲突，沿用是安全的——这正是
M0 选 UUID 而不是自增整数的那个理由在这里兑现。

课程则按**名字**合并。换一台机器导入时，同名课程几乎总是同一门课，而 id 一定
不同；按 id 的话会凭空多出一门重名课程，侧栏里两个「数据结构」。

试卷按 id 认重、从不合并。「合并两份试卷」没有语义，但同一个包导两次不该变出
两份一模一样的卷子——备份重复导入是最常见的误操作，而多出来的那份和原件长得
一模一样，发现时已经分不清哪份是哪份。

### 一个被测试逼出来的 bug：身份映射会留着已经删掉的行

删课程走的是数据库级联（`passive_deletes=True`），SQLAlchemy 并不知道那些
Question 没了，**身份映射里还留着**。于是同一个会话里 `session.get(Question, id)`
会把一个已经不存在的行交回来。交换包据此去接试卷的 `question_id`，插入时就是
一个 `FOREIGN KEY constraint failed`——而「删掉课程再从备份恢复」恰恰是这个包
存在的理由。

两处都修了：判定「这道题在不在」先查一次数据库，不信身份映射；
`delete_course` 之后对整个会话 `expire_all()`。

### 批量操作仍然逐题留历史

批量改恰恰是最该能撤销的：一次点错影响几十道题，而「改错了，一道道改回去」
根本不现实。代价是几十条快照，相比之下不值一提。

但**没有实际变化的题不记历史**——批量把 50 道题都设成它们本来就是的值，不该
产生 50 条无意义的记录。只有标签变动才重建索引：标签进全文索引，章节、难度、
状态不进。指纹完全不用重算，这四样都不参与指纹。

### 桌面外壳只是个窗口

里面跑的是和 `qbank serve` 完全一样的那个 FastAPI 应用，一行业务代码都不一样。
这正是 M0 定下的分层要换来的东西。

服务跑在后台 daemon 线程而不是子进程：窗口一关进程就退，不留垃圾。端口每次现
问系统要一个空的——硬用 8765 的后果是窗口打开后显示的是**另一个实例**的页面，
诡异到无法排查。

### 打包：漏一个数据文件会在用到的那一刻才炸

PyInstaller 默认只收 `.py`。少了 `latex2mathml` 的符号表，Markdown 导出一切正常，
一导 HTML 就 `FileNotFoundError`——而构建过程一个警告都没有。所以 spec 里显式
列出了每个会在运行时读自己数据文件的包，并有测试守着这张清单。

冻结之后 `__file__` 推不出项目根，要认 `sys._MEIPASS`。不处理的话
`_head_revision()` 会吞掉异常返回 `None`，于是打包版**永远不跑数据库迁移**，
升级后打开旧题库表结构还是旧的，程序一声不吭。

包里捆 pandoc（110 MB）不捆 playwright（140 MB）：Word 导入导出是目标用户的
刚需，而 PDF 有「导出 HTML 再浏览器打印」这条等价退路。打包版里凡是
「装个什么就好了」的提示都要先问一句 `is_frozen()`——包是只读的，`pip install`
是一条走不通的路。

## 十一、Web 部署：换后端、加鉴权，内核一行没改

分层约束（`tests/unit/test_layering.py`）从 M0 就在那儿，M7 是它的兑现检验。
结论：`core` 与 `exchange` 两个包**一行没改**，改动全在 `qbank.web`、
`qbank.core.db`（引擎与 DDL）和配置层。

### Postgres 的中文检索必须绕开它自己的分词器

这是 M7 唯一一个「不验就会在线上才发现」的坑。实测（PostgreSQL 16.15，UTF8 库）：

```
SELECT to_tsvector('simple', '栈 图 最短 cpp');
 -> 'cpp':4
```

`default` 解析器把中日韩字符判成 `blank`（token 类型 12，「Space symbols」），
中文 token 一个都不剩。如果照常规写法用 `to_tsvector`，部署之后的症状是
**搜英文能搜到、搜中文永远空**，而索引表看起来是满的——没人会想到去怀疑分词器。

解法和 SQLite 侧是同一个思路：**分词在 Python 里做完**，数据库只负责存和匹配。
SQLite 用 `unicode61`（它不切中日韩，只按空格断开），Postgres 则把切好的 token
拼成 `tsvector` 字面量直接转型写入，完全不经过解析器与词典：

```
'栈':1A '图':2A '树':3B '解':4C
```

位置编号只为承载权重标签——没有位置的 tsvector 存不下权重（实测
`setweight(array_to_tsvector(...), 'A')` 是空操作）。超过 16383 的位置会被 Postgres
静默压到 16383，不报错，超长题目的词频到那里饱和而检索仍然正确。

于是两种后端索引的是**同一批 token**，命中集合完全一致，不是「大致相同」。
`tests/integration/test_postgres.py::test_both_backends_return_the_same_hits`
用同一批语料在两个库上跑同一组查询，逐条比命中集合。

排序分数不一致是接受的：bm25 返回负数（越负越相关），`ts_rank` 返回正数
（越大越相关），两边都得满足「`score` 越小越相关」这个契约，所以 Postgres 侧取了负号。
权重 A=1.0 / B=0.5 / C=0.2 与 SQLite 侧的 bm25 权重 10 / 5 / 2 等比。

### 一处被 Postgres 逼出来的旧 bug：标签没有排序

同一道题，SQLite 显示「队列、栈」，Postgres 显示「栈、队列」——`Question.tags`
关系上没写 `order_by`，顺序由数据库决定。这在单后端时代看不出来，但标签会进导出
产物，而「同一份卷导出两次字节一致」是 M5 明确承诺过的。加了 `order_by="Tag.name"`。

### 认证做成接入点，不是用户系统

题库里没有「用户」这个概念：题目不属于谁，也没有按人分权的需求。真正要解决的是
「谁能打开这个地址、谁只能看」，而这件事在不同部署里由完全不同的东西决定——
一个教研室一个共享口令就够，一所学校则已经有统一身份认证。所以做成三种策略
（`open` / `password` / `header`），由环境变量选，路由与模板一行不碰。

三条刻意的「宁可起不来」：`password` 模式没给口令、`header` 模式没给头名、
`QBANK_AUTH` 写错一个字母——都直接抛异常拒绝启动，不退回 `open`。
**一个以为自己有鉴权、实际敞开的部署，比一个起不来的部署危险得多。**

会话密钥默认从口令派生而不是随机生成。随机的话，多 worker 各自一个密钥，
症状是「会话随请求落到哪个进程而随机失效」，日志里什么都看不出来；单进程随机则
每次重启把所有人踢下线。派生还顺带给出一个正确的副作用：改口令立刻作废全部现有会话。

### 只读身份：界面藏按钮是体面，中间件 403 才是防线

`base.html` 里一条 CSS 规则把所有 `form[method="post"]` 藏掉，而不是在四十多个表单上
逐个加 `{% if can_edit %}`——一条规则覆盖全部，连以后新加的表单也自动算进去；
逐个加判断则是漏一个就留一个按不动的按钮。

但那只是不让人白点。真正的拦截在访问控制中间件，而「真正」必须是可枚举的：
`test_every_write_route_is_blocked_for_a_viewer` 从路由表现算出所有 POST 路由，
逐条断言只读身份拿到 403。以后新加一条写路由，它自动进入这个测试。

### 跨站写请求：查同源，不发 CSRF token

CSRF 的本质是「浏览器带着用户的凭据，去执行别处页面让它执行的请求」——攻击一定由
浏览器发起。而现代浏览器在跨站表单提交上必然带 `Origin`（或 `Sec-Fetch-Site`），
这两个头脚本都改不了。所以「头在、且不是本站」即可判定并拒绝。token 方案能多防住的
只有「不发 Origin 的浏览器」，那类浏览器已经不存在了；代价却是要落到四十多个表单上，
漏一个就是一个静默的洞。

比的是 `Origin` 的 netloc 与 **`Host` 头**，不是 `request.url`：反向代理后面
`request.url` 要靠 `--proxy-headers` 才正确，而 `Host` 就是浏览器实际用的那个名字。
代价是代理必须透传 Host——配错时的症状很有特色：**所有写操作 403，读完全正常**，
这一条写进了部署指南的故障表。

这层防护在不鉴权模式下也开着：`qbank serve` 绑在 127.0.0.1 上，任何网页都能向它发
跨站表单提交，而那里没有鉴权——「只有本机能连」挡不住这个。

### 上传要边读边判大小

原先是 `await file.read()` 读完整个请求体再交给暂存层判断大小。本地客户端无所谓，
放到网上就是一条内存耗尽的路子：谁发一个几 GB 的请求体，worker 就分配几 GB 然后被
OOM 杀掉，而那句大小检查永远轮不到执行。改成分块读、超限立刻停。

代理那边也该设一道（`client_max_body_size`），但应用不能依赖它——直连应用端口的
请求绕过代理。

### 数据目录仍然是本地的

换了 Postgres 之后，图片、导入暂存、导出产物仍然落在 `QBANK_DATA_DIR` 下。
一台机器多 worker 没问题；多台机器则必须共享那个目录，否则图片只在上传的那台机器上。
对象存储要在 `qbank.config.Paths` 那一层加存储抽象，还没做。

## 十二、还没做的

- 图片的对象存储（见上一节最后一段）
- 按人分权（只有「可编辑 / 只读」两档，没有用户表；修改历史记的是改了什么，不是谁改的）
- 共享口令没有尝试次数限制，公网部署要在代理层加限流
- macOS / Windows 的代码签名与公证
